The Lesson: Rules, Not Typists

The posting engine is a simple idea with strict discipline: for each business event, a pre-agreed RULE decides the journal entry. Humans approve events; the engine writes numbers. No typists.

A posting rule answers four questions for its event:

  1. Which accounts? (Dr Inventory—Yarn / Cr AP—Import LC)
  2. Which amounts? (GR quantity × LC rate)
  3. When is it allowed? (sequence checks — see below)
  4. Which subledger rows? (AP row for ABC Yarn, inventory lot row)

Sequence validation — where naive systems die

A mathematically perfect entry can still be logically impossible. Real factories have an order of life, and the engine must enforce it:

  • No R4 shipment revenue without an approved order and a B/L date.
  • No R5 COGS before R4 — you can't expense goods that haven't shipped (Module 6!).
  • No supplier payment R7 before its GRN (R1) exists — pay only against proof.
  • No R2 issue of more yarn than lot 2026-C-118 contains.

Sequence errors create entries that balance perfectly and describe nothing that ever happened — the worst kind of lie, because it passes every arithmetic check.

Rules live in CONFIGURATION, not code

Which account receives yarn? That's a business decision that changes (new plants, new account structures). If Rafiq hardcodes "1211" inside a function, every change becomes a deployment. The professional pattern: rules stored as versioned configuration — the engine reads them at runtime, and every posted entry stores WHICH rule version created it.

There are no dumb questions
If the engine writes everything, do accountants become useless?
Opposite — they level up. Instead of typing thousands of lines, Shirin designs rules, investigates exceptions, and signs reconciliations. The engine handles volume; humans handle judgment.
What if Jamal approves a GRN by mistake?
The entry exists because approval happened — so corrections go through document flows: cancel/amend the GRN with approval, which triggers a REVERSING entry. Nobody edits or deletes journal lines. Ever. (Module 12 formalizes this.)
Can two rules fire for one event? Like VAT on a purchase?
Yes! One event can produce a MULTI-LINE entry (or several): Dr Inventory + Dr VAT Input / Cr Supplier. Complex rules compose from simpler ones — but each line still traces to the same source document.

Exercise 2 — Refuse these postings

For each request, cite WHICH sequence check rejects it:

  1. "Post COGS for H&M invoice INV-9000." (No INV-9000 in AR subledger.)
  2. "Pay Delta Textile ৳18 lakh today." (Their fabric GRN is still draft.)
  3. "Issue 6,000 kg from yarn lot 2026-C-118." (Lot holds 5,000 kg.)

Solution to Exercise 2:

  1. R5 requires R4 first: no shipment invoice → no COGS. Postings must trace to existing documents.
  2. R7 requires R1 first: pay only against approved receipts. Draft ≠ approved; the proof doesn't exist yet.
  3. Quantity availability check on R2: issuing beyond lot balance would push inventory negative — physically impossible, therefore financially forbidden.

From Lesson to Software

Before you take the quiz, write the software specification a developer would need to build the posting logic from this module. Predict first, then reveal the model answer.

1. What event triggers this posting?

A source document has been approved — for example a GRN signed by store and QC, an approved supplier invoice, or a payment voucher released by finance. The trigger is the approval event, not the upload; an unapproved document never reaches the engine.

2. Which accounts, amounts, and dates apply?

Example for a yarn arrival: Dr Inventory—Yarn / Cr Accounts Payable—ABC Yarn. The amount comes from the GRN (quantity × agreed price), and the date is the GRN date, not the moment the engine ran. One event in, one balanced journal out.

3. What approval and validation are required?

Event status must equal “approved”. The amount must match the source document to the last taka. The entry must balance, the accounts must exist in the COA, the accounting period must be open, and maker-checker separation must be enforced (the approver is not the preparer).

4. What happens on cancellation, correction, or retry?

If approval is revoked, the engine reverses the generated journal on the revocation date, preserving the original reference and the full audit log. The original entry is never edited or deleted — corrections are always separate reversing or adjusting entries that point back to the source.
