The Lesson: The Company's Filing Cabinet

A Chart of Accounts (COA) is the complete, ordered list of every account the company uses — nothing more, nothing less. Think of a filing cabinet where every folder has:

  • a code (so everyone means the same folder),
  • a name (so humans can find it), and
  • a type (Asset / Liability / Equity / Revenue / Expense — remember DEA-LER?).

The type matters enormously: assets and expenses roll into the Balance Sheet's left side or the Income Statement; revenues, liabilities, and equity fill the rest. The COA is literally the skeleton that financial statements hang on.

Codes are not random. The first digit tells you the type, so you can read any account code like a postcode:

The three COA design rules

  1. One home per concept. "Repairs" lives in exactly ONE account (say 7310). Two names for one idea = the Shirin mystery at the start of this module.
  2. Detailed enough to manage, simple enough to close. Every account must have a decision attached to it ("what will we DO differently when this number changes?"). An account nobody ever uses for decisions is noise.
  3. Frozen codes, living descriptions. Codes never get recycled or renumbered once transactions exist — reports and integrations depend on them. Need a new account? Append, don't rewrite.
There are no dumb questions
Why numbers at all? Names feel friendlier.
Because "Inventory—Yarn" and "Yarn Stock" and "Yarn" would become three folders in real life. A code forces one identity; the name is just its label. Machines join on codes, humans read labels.
Do we need separate accounts for each buyer, like H&M vs Zara?
Good instinct — but usually NO, not in the COA. Buyer detail belongs in the subledger (next module!). The GL keeps one Receivable account; the subledger keeps H&M, Zara, C&A rows underneath it. Confusing these two layers causes real pain — that's Module 3's whole story.
Can't we add accounts whenever someone asks?
Only through a small approval gate (finance + the ERP owner). Otherwise the cabinet fills with duplicate folders within a year — ask anyone who has maintained an uncontrolled COA.

Exercise 2 — Fix the cabinet

Three change requests arrive at the same time: (a) rename account 7310 from "Repairs & Maintenance" to "Repairs"; (b) create a new account "Glue & Chemicals"; (c) recycle unused code 5555 for "Marketing". Which do you approve as-is, which with conditions?

Solution to Exercise 2:

(a) Approve. Renaming a label is safe — code 7310 stays, history stays truthful. (b) Approve with a check: does a chemicals-type account already exist? If glue was being dumped into 7310 or stores, plan the migration date, otherwise comparisons break mid-year. (c) Reject the recycle. Even if 5555 looks unused, verify zero historical transactions first; if any exist, take a fresh code (e.g. 8100). Recycling codes is how old reports start telling new lies.

Exercise 3 — Guided: choose a home and a decision

Masco begins tracking generator diesel separately because monthly usage is rising. You are given the first digit rule: 1 = asset, 5–9 = expense. Decide the type, a possible code, whether it deserves a separate account, and what decision the account supports.

Guided answer:

Diesel kept for use is an inventory asset (a 1xxx code); diesel already consumed may be a direct or operating expense under the costing policy (a 5xxx–9xxx code). For this exercise, choose a separate expense account such as 7410 Generator Fuel because management can compare generator usage, investigate abnormal consumption, and budget it. The exact number is a Masco design choice, not a universal accounting code. If fuel is first stocked, the receipt may debit Inventory—Fuel; an issue to the generator moves it to expense or production cost.

Why not “Other Expenses”? That would hide a controllable cost and answer no management question. Why not one account per generator? Use a dimension — a reporting tag (machine, department, or order number) attached to postings so reports can slice one account's balance without creating new GL accounts — or asset-level detail when the decision needs that breakdown; do not multiply the GL without a reporting reason.

Exercise 4 — Independent: design one new account

A new compliance report needs VAT Input separated from ordinary purchases. Assumption: registered suppliers issue VAT invoices that state recoverable input tax separately from the price (rates and law live in Module 14 — none are needed here). Propose an account name, type, code block, one source document that posts to it, and the decision its balance supports. Then explain why the supplier’s name belongs in detail rather than in the account name.

Independent answer:

One defensible design is VAT Input Receivable, Asset, in the 1xxx block (for example 1410), posted from an approved VAT invoice or purchase document. Its balance supports the VAT return reconciliation and shows the recoverable input tax. The supplier is recorded as subledger detail linked to the control account, because adding a new GL account for every supplier would make the chart unwieldy and break consistent reporting.

Build it yourself

Classify these into the right block (which first digit?) AND decide if they deserve to exist as separate accounts: (1) Diesel for generators, (2) Money H&M owes us, (3) The machines in the dyeing hall, (4) A vague "Other" account for anything uncategorized.

Solution:

  1. Diesel → Expense block (e.g. 74xx). Yes — energy is a huge, manageable cost.
  2. H&M receivable → Asset block (13xx control account). But buyer detail goes in the SUBLEDGER, not a dedicated COA line per buyer (Module 3!).
  3. Dyeing machines → Asset block, Fixed Assets section (15xx). Yes — depreciation depends on it (Module 10).
  4. "Other" → Reject. An everything-account is where errors hide; auditors call it a garbage barge. Every posting must have a specific home.

From Lesson to Software

Before you take the quiz, write the software specification a developer would need to build the posting logic from this module. Predict first, then reveal the model answer.

1. What event triggers this posting?

A new account is needed, an existing account is renamed or remapped, or a subledger is attached to a control account. The Chart of Accounts is a living structure, and every change to it is an event the system must record.

2. Which accounts, amounts, and dates apply?

The fields are the account code, the account name, the type (asset, liability, equity, revenue, expense), the normal balance (debit or credit), the parent summary account, and a subledger flag if the account has party-level detail. The effective date is when the change goes live; old accounts keep their historical postings.

3. What approval and validation are required?

No duplicate code or name allowed. The account type must come from the allowed list (the five blocks). If the subledger flag is on, it must point to exactly one control account. Every change must be approved by finance (and IT for renumbering), with maker-checker separation.

4. What happens on cancellation, correction, or retry?

Renumbering requires a migration with an effective date; do not retroactively rewrite historical entries. If an account is no longer needed, deactivate it instead of deleting it — historical postings still reference it and the audit trail must stay intact. Every change is logged with who, when, and what.

Key Takeaway: The COA is the master filing system: every journal line points to exactly one account, every account earns its place with a decision it supports, and codes are frozen forever once used. Build it before building software — the database, the reports, and the audits all stand on it.
